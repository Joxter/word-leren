## Контекст

Есть приложение для карточек. Текущий планировщик: одна явная очередь, карточка
берётся сверху, после ответа вручную отправляется на +8 / 20 / 50 / 100 / 250 /
500 / 1000 / 2500 / 5000 позиций вперёд. Никаких дней, лимитов и списка
просроченного. Это осознанное решение, а не недоработка.

Задача — заменить ручной выбор позиции на модель памяти FSRS, **сохранив
принцип одной очереди и полностью отказавшись от дневных дедлайнов**.

## Ключевое архитектурное решение

Разделяем три вещи, которые в Anki слиты:

| Часть                           | Кто отвечает               |
| ------------------------------- | -------------------------- |
| Состояние карточки (D, S)       | FSRS через `ts-fsrs`       |
| Правило пересчёта после ответа  | FSRS через `ts-fsrs`       |
| Диспетчер — что показать сейчас | **наш код, не библиотека** |

Диспетчер: **одна очередь, отсортированная по возрастанию R** (retrievability).
Сверху — то, что вероятнее всего забыто. Берём сверху.

Позиция карточки больше нигде не хранится — порядок вычисляется из состояния.
Время двигает карточки вверх само.

## Чего в системе НЕ должно появиться

Это важнее половины требований ниже:

- нет поля `due` и запроса «что просрочено на сегодня»;
- нет счётчика вида «к повторению: 847»;
- нет дневных лимитов на повторения;
- нет отдельных колод/вкладок new / learning / review в UI.

Пропуск недели не должен порождать никакого долга. Он меняет только порядок
внутри очереди.

## Библиотека

`ts-fsrs` (npm, требует Node >= 20). Использовать **низкоуровневый API**, не
`repeat()` / `next()` — они возвращают готовые даты, а даты нам не нужны:

```ts
import { fsrs, Rating, type FSRSState } from "ts-fsrs";

const scheduler = fsrs({ request_retention: 0.9, enable_fuzz: false });
const next = scheduler.next_state(memoryState, elapsedDays, rating);
// -> { stability, difficulty }
```

`enable_fuzz` можно выключить: fuzz нужен, чтобы карточки не слипались в один
день, а у нас дней нет. Но проверить, не слипаются ли они по R.

Для тренировки параметров на логах позже — `@open-spaced-repetition/binding`.
Сразу его не подключаем, стартуем на дефолтных весах.

## Модель данных

```ts
type Card = {
  id: string;
  front: string;
  back: string;

  // FSRS
  stability: number | null; // null = ещё не показывали
  difficulty: number | null;
  lastReviewedAt: number | null; // unix ms, для расчёта elapsed

  // лестница уровней
  level: 0 | 1; // 0 = узнаю (RU->target), 1 = перевожу (target->RU)
  spelling: boolean; // требовать ввод текста, ставится вручную

  suspended: boolean;
};

type ReviewLog = {
  cardId: string;
  reviewedAt: number;
  rating: 1 | 2 | 3 | 4;
  elapsedDays: number;
  stabilityBefore: number | null;
  difficultyBefore: number | null;
  stabilityAfter: number;
  difficultyAfter: number;
  level: 0 | 1;
  source: "session" | "field" | "manual";
};
```

`ReviewLog` пишем с первого дня и никогда не чистим — это единственный вход для
будущего оптимизатора параметров. Схема должна совпадать с тем, что ожидает
`@open-spaced-repetition/binding` (проверить формат в его README).

## Расчёт R и порядок очереди

```
R(t, S) = (1 + (19/81) * t/S) ^ (-0.5)
```

где `t` — прошедшее время с `lastReviewedAt` **в днях, дробное**.

Очередь = все карточки с `stability != null` и `!suspended`, отсортированные по
R по возрастанию. Пересчитывать R при открытии сессии и после каждого ответа
(достаточно, если очередь держится в памяти и пересортировывается лениво).

Если у верхней карточки `R > 0.9` — показать состояние «на сегодня всё, долга
нет». Это должен быть заметный позитивный сигнал в UI, а не пустой экран.

## Новые карточки

У новой карточки R не определён, в общий порядок она не встраивается.
Единственный ручной кран: кнопка **«добавить N новых»** (N по умолчанию 10,
настраивается). Она берёт N карточек из пула неизученных и кладёт их в
буфер текущей сессии.

Внутриcессионный буфер нужен потому, что только что показанная новая карточка
получает R ≈ 1 и мгновенно уходит в самый низ, хотя повторить её надо через
несколько минут. Реализация: карточки со `stability < 1 день` живут в отдельном
списке в памяти сессии и переоцениваются по минутам, а не по дням. При
завершении сессии буфер просто растворяется — карточки уже имеют S и D и
встраиваются в общую очередь.

При старте новой карточки использовать `enable_short_term: true` в конфиге
`ts-fsrs`, чтобы обновление S для внутридневных повторов было корректным.

## Оценки

Четыре кнопки вместо девяти: **Again / Hard / Good / Easy** → `Rating` из
`ts-fsrs`. Семантика меняется с «куда отправить» на «как прошло вспоминание».
Интервал теперь вычисляется, а не выбирается.

## Лестница уровней

`level` — поле карточки, не глобальный режим. Вопрос рендерится по уровню:

- `level 0` — узнавание, показываем слово на изучаемом языке, ждём смысл;
- `level 1` — продукция, показываем русский, ждём слово.

Правила:

- `Again` → `level = max(0, level - 1)` (понижение на одну ступень, не в ноль);
- `Easy` при `level 0` и `stability > порог` → `level = 1`, и при этом
  **S принудительно ужимается** (например, `S = min(S, 3)`), потому что новый
  уровень ещё ни разу не проверялся. Порог повышения сначала захардкодить и
  вынести в конфиг — данных для его подбора пока нет.

`spelling` — отдельный булев флаг, а не третья ступень. При нём в UI появляется
поле ввода, ответ диффается с эталоном и ошибки подсвечиваются, **но оценку
всё равно ставит пользователь** — опечатки и синонимы он засчитывает как успех
сам. Автоматически оценку по диффу не выставлять.

## Ручные операции

1. **Поиск и показ вне очереди** — нашёл карточку, ответил, состояние
   пересчиталось обычным путём. Никаких особых веток.
2. **«Встретил в жизни»** — то же самое, но `source: 'field'` в логе. Это самый
   ценный сигнал в данных: провал в реальном тексте ≠ провал на сороковой
   минуте сессии.
3. **«Знаю намертво, отстань»** — задрать `stability` вручную (умножить на
   коэффициент или выставить фиксированное большое значение). Логировать как
   `source: 'manual'`, чтобы такие записи можно было исключить при тренировке
   параметров.
4. **Suspend** — исключение из очереди без потери состояния.

## Фильтр усталости

Поверх той же очереди, без создания второй очереди и без изменения состояния:
чекбокс «только лёгкое» → фильтр `difficulty < 5`. Безопасен именно потому, что
провал понижает `level`: трудное слово сползает на «узнаю» и попадает в лёгкий
фильтр само, а не оседает в отстойнике.

## Порядок реализации

1. Схема данных + `ReviewLog`, пишущийся при каждом ответе. Ничего не меняя
   в текущем UX.
2. Расчёт R и сортировка очереди по нему, за фиче-флагом, рядом со старой
   очередью. Сравнить порядок глазами.
3. Четыре кнопки + `next_state`, замена ручных прыжков.
4. Буфер новых карточек и кнопка «добавить N».
5. Уровни: сначала только понижение при `Again`. Повышение — позже.
6. `spelling`, фильтр усталости, ручные операции.

## Миграция

Старые логи движений (`+250` и т.п.) не конвертируются в D/S напрямую —
семантика разная. Варианты обсудить, не выбирать в одиночку:

- стартовать все карточки с нуля как новые (честно, но больно);
- эвристически проинициализировать `stability` из последнего ручного прыжка,
  поделив на среднюю дневную пропускную способность (карт в день за последние
  2 недели), `difficulty` оставить дефолтным.

Второй вариант предпочтительнее, но нужно посчитать реальную пропускную
способность по имеющимся логам перед тем, как выбирать коэффициент.

## Тесты

- R монотонно убывает по времени и растёт по S;
- `Again` никогда не обнуляет S (карточка с S=300 после провала должна
  оказаться в районе 20-40, а не 1);
- D возвращается к среднему: серия `Again` с последующей серией `Good` должна
  восстанавливать difficulty, а не запирать карточку навсегда;
- пропуск 30 дней не создаёт никакой очереди «просроченного», только меняет
  порядок;
- новая карточка, отвеченная `Again` дважды подряд внутри сессии, показывается
  снова в этой же сессии.
